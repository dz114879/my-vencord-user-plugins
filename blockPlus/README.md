# BlockPlus

## 简介

`BlockPlus` 是一个比 Discord 原生屏蔽更细粒度的屏蔽插件。它提供三种模式，分别解决“完全不想看到这个人”，“只想隐藏这个人本人的消息”，“已经原生屏蔽，但自己又想看见对方消息”这几类不同需求。

插件会在整个界面右上角加入一个 `BlockPlus` 按钮，用来集中管理规则。

## 使用方式

1. 启用插件后，打开任意频道。
2. 点击右上角的 `BlockPlus` 按钮。
3. 手动输入用户 ID，选择模式后添加。
4. 已添加的用户会显示在列表中，可以随时删除。

规则会按当前 Discord 账号单独保存。

## 三种模式

- `彻底屏蔽+`：**无需使用DC原生屏蔽。**，隐藏该用户自己的消息；也隐藏“回复该用户”或“提及该用户”的消息。
- `彻底屏蔽`：**无需使用DC原生屏蔽。**，隐藏该用户自己的消息；其他人提及该用户的消息照常显示；如果是回复该用户，则仅移除回复引用区，正文保留。
- `单向屏蔽`：**必须先使用 Discord 原生屏蔽**。在你自己的视角下，对方消息会恢复正常显示，不再以原生“已屏蔽消息”分组的方式折叠。

## 请注意！

如果你已经用DC原生屏蔽，屏蔽了一个用户，`彻底屏蔽+` 和 `彻底屏蔽` **不会** 隐藏他们的'X条已屏蔽消息'。这两个模式是给你不想使用DC原生屏蔽时准备的，对方无法知道你屏蔽了他。

如有隐藏'X条已屏蔽消息'的需求，请使用Vencord自带的Plugin: `NoBlockedMessages` 。

## 兼容性与实现备注

### 现状（2026-04-15）

在当前这套 Vencord 代码和本次测试对应的 Discord 前端版本里，`BlockPlus` 这类“隐藏消息 / 隐藏回复引用”的逻辑，已经不能再依赖 `channelStream` 级别的补丁入口。此前尝试挂在 `.Messages.CHANNEL_MESSAGES_A11Y_DESCRIPTION` 上改 `channelStream`，虽然构建能过，但运行时完全不触发，日志也证明进入频道后没有任何 `transformChannelStream` 调用。

换句话说，这条入口在当前版本里已经不可靠。

### 当前可靠链路

当前有效实现基于消息 `<li>` 渲染层，也就是 [`index.tsx`](./index.tsx) 里的消息节点补丁：

1. 给消息 `<li>` 注入 `data-blockplus-author-id`、`data-blockplus-reply-author-id`、`data-blockplus-mention-ids`。
2. 首次渲染时，直接给消息节点打上 `vc-blockplus-hidden` 或 `vc-blockplus-strip-reply`。
3. 当规则发生变化时，主动扫描当前 DOM 上已经存在的消息节点，重新同步 class。
4. 再由 [`style.css`](./style.css) 统一隐藏整条消息或 reply preview。

### 已验证有效的行为

- `彻底屏蔽+`：隐藏被屏蔽者自己的消息，也隐藏“提及该人”或“回复该人”的消息。
- `彻底屏蔽`：隐藏被屏蔽者自己的消息；其他人回复该人的消息正文保留，但回复引用区整块隐藏。
- `单向屏蔽`：继续保留原先的分组修正逻辑，不让 mode 3 被当成 Discord 原生 blocked 分组。

### 为什么回复引用改成 CSS 隐藏

当前版本里，回复引用不是靠在 reply 子组件里 `return null` 实现，而是给整条消息 `<li>` 加 `vc-blockplus-strip-reply`，再用 CSS 隐藏这些 reply 相关节点：

- `[class*="repliedMessage"]`
- `[class*="replyAvatar"]`
- `[class*="repliedTextPreview"]`
- `[class*="repliedTextContent"]`

这比“在 reply 子组件里直接返回空”稳定得多。之前出现过“用户名没了，但头像和引用内容还在”的情况，本质上就是补丁挂得太晚，或者命中范围不完整。

### 以后维护时的优先级

1. 先验证补丁点在运行时是否真的触发，不要只看构建是否通过。
2. 消息隐藏优先挂在消息 `<li>` 层，而不是 `channelStream`。
3. 动态增删规则不要依赖 React 强制刷新；直接扫描当前 DOM 并重算 class 更稳。
4. 回复引用隐藏优先走“整条消息节点加 class，再用 CSS 隐藏 reply preview”，不要优先回到 reply 子组件 `return null`。
5. 排查问题时，先看这三件事：
   - 补丁点有没有命中。
   - 命中后有没有成功注入 `data-*`。
   - 注入后类名切换有没有真实发生。

## 总结

当前版本里，`BlockPlus` 真正可靠的实现方式是：

`消息 <li> 补丁命中 -> 注入 data-* 和 class -> DOM 扫描同步旧消息 -> CSS 隐藏消息或回复引用`

如果后续继续维护这类插件，建议继续围绕这条链路迭代，而不是回到已经失效或不稳定的旧入口。
